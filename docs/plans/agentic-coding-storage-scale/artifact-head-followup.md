# Artifact head payload follow-up

**Status:** Awaiting the user’s D-9 refinement decision (asked 2026-10-04). This proposal does not amend the approved Specification or authorize payload pruning. Existing implementation and tests continue.

## Current boundary

D-9 keeps the current artifact head and a bounded recent version window in PostgreSQL; older encrypted versions and diffs can move to S3. This bounds history per artifact, but does not bound account-wide warm bytes when new artifacts keep arriving. The accepted heavy-user workload includes 200 new embeds and 1000 file versions/diffs per day. Neither that workload nor the recent-version window is an account quota.

The scheduled cold-chat task currently archives message segments. The older whole-chat `ColdArchiveService.archive_chat` has no product caller; if activated as written, it would copy and delete whole embed rows without a Project or cross-chat reference fence and would omit `embed_diffs`. It must not serve as a shortcut for current-head payload eviction. The existing version archive handles historical rows, not the current `embeds.encrypted_content` head.

## Minimal archive-aware current-head reader

Retain the embed row and its stable identity in PostgreSQL: `embed_id`, owner/chat scope, version/head generation, current encrypted metadata, timestamps, reference and key-wrapper relationships, and a durable payload locator, byte length, digest, and copy/read/prune state. Archive only an immutable copy of **current-head ciphertext bytes**. A metadata page must stay small; an authorized exact payload read may use a separately bounded response for an oversized head. Never return an S3 object key or bypass the existing client-side decryption boundary.

Put one shared payload resolver behind all exact embed reads. It must check the live access scope before object access: personal owner, current Team membership and chat scope, Project membership plus target reference, or a currently valid public share. It then reads either the PostgreSQL payload or the verified object for the requested head generation. Verify length and digest and surface an authorized storage/integrity failure; do not convert that failure into a missing/private dummy embed or an empty ciphertext. Keep response identity and ciphertext shape compatible with existing consumers. Chat and share metadata windows should resolve payloads only for the admitted page or explicitly selected embed, preserving byte caps and continuation cursors.

The resolver must cover the private `/v1/embeds/{embed_id}/encrypted` Project route, chat sync/window and exact embed routes, shared-chat window/exact embed and `/share/embed/{id}`, SDK and CLI reads including version restore, web embed resolution, native chat/embed reads, and encrypted account export. Export currently iterates `embeds` rows with `fields=*`; it must hydrate each authorized head through the resolver in bounded chunks and record integrity failures rather than silently exporting a metadata-only row. Historical-version reads remain on their separate version archive path. Reader coverage should be checked at API boundaries used by native clients, not inferred from web success.

## References, writers, and rollback

Archiving a payload is **not deletion of the artifact**. Retain the current embed identity, ownership, wrappers, graph links, and version metadata so Project items, other chats, Team readers, shares, and older version reconstruction still resolve. A reference check must precede actual embed/key deletion, not merely payload copying. D-11 requires shared files to follow their references independently of chat age. A currently referenced head may have its ciphertext copied only after every authorized path can read the archive; it cannot disappear because its creation chat became inactive.

Serialize copy activation and payload pruning against head writes using an embed-scoped lock or compare-and-swap over `(embed_id, version_number, head_generation)`. A writer publishes a new immutable generation; a stale copy must never replace or prune that new head. Retain the PostgreSQL source through copy, checksum and regional durability verification, reader enablement, and a rollback window. Prune only the matching payload field after every supported reader is archive-aware and pending client-encrypted writes/recovery acknowledgements are settled. Keep old generations while referenced by a reader or version transition. If object validation fails, leave the PostgreSQL source intact and retry; after pruning, fail visibly rather than serving stale ciphertext. Rollback must be able to switch back to retained PostgreSQL bytes or a verified prior copy, with locator/state changes audited and idempotent.

## Account-wide warm-byte policy requiring a D-9 decision

Under **approved D-9**, current-head ciphertext stays in PostgreSQL. An account that creates new artifacts indefinitely therefore accumulates current-head bytes even if each artifact has at most a bounded recent diff window. Admission/usage quotas or retention terms could cap that growth, but no such quota is approved here. The implementation must report total hot head bytes and recent diff bytes per owner separately; a 32-version gap/window is not a 32-row cap and is not a bound on the number of artifacts.

A possible **unapproved D-9 refinement** would keep current-head identity and small metadata in PostgreSQL but permit verified S3-backed ciphertext heads after an explicit activity and byte-budget policy. Apply an owner-wide warm-byte target to the sum of hot head and recent-diff payloads, selecting inactive, safely copied generations by age/size until under target. Define activity from actual Project/chat/native/CLI/export use and active writers, with a bounded lookback; a head merely referenced by a Project remains readable but need not consume warm PostgreSQL bytes once its reader is archive-aware. Track any active/pinned/recovery exceptions as visible budget debt, not as silent eviction or content destruction. Set the target, recency, exceptions, and Team accounting only after a separate product decision; do not treat the accepted heavy-user workload as a quota. If D-9 is not refined, describe account-wide warm growth honestly and use bounded reads and capacity measurement without claiming fixed PostgreSQL payload usage.

## Implementation touchpoints and proof

Likely touchpoints: `services/directus/embed_methods.py` for a metadata-only lookup and strict payload resolver; `routes/embeds_api.py`, `sync_api.py`, `share.py`, and SDK routes for scope-preserving reads; `services/account_export_service.py` for complete ciphertext export; CLI, web embed resolver, and native API consumers; a new head-copy intent/locator schema and worker modeled on the historical version archive's verified copy lifecycle. Do not route this through whole-chat graph deletion.

Essential focused tests: Project and cross-chat referenced heads survive creation-chat inactivity; Team revocation and public-share visibility are rechecked before object reads; each private/shared/SDK/CLI/web/native/export path returns the exact same ciphertext and head generation after PostgreSQL payload pruning; metadata paging and oversized exact reads stay bounded; copy, region, checksum and object failures propagate; concurrent head update defeats stale activation/prune; pending client-encrypted writes defer pruning; retry and rollback restore the same head; per-owner accounting includes many newly created artifacts as well as recent diffs. No real inference is required.

**Blocking decisions and gates:** an approved D-9 refinement for current-head payload eviction and any owner-wide target; complete supported-client reader coverage; a durable head-generation/intent transaction and reference inventory; verified object durability and rollback evidence. Until those gates are met, copying ciphertext is safe to develop, but pruning current-head PostgreSQL bytes is not.
