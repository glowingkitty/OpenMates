# Why OpenMates releases get stuck

24 November 2026

OpenMates makes one release decision out of three separate questions. Is the shared test version safe for customers? Can it be combined with the fixes already in production? Has every unfinished workspace been accounted for? Today the workspace check and the branch comparison both found blockers. The workspace check by itself says nothing about whether customers would encounter a broken feature.

## 1. How a change reaches customers today

1. **The chat works in its own copy.** A session is the record linking a Task and a chat to a private working copy, called a worktree. It starts from `dev`, the shared development branch. The worktree does not need a branch of its own. Its changes stay there until the chat publishes them.
2. **The deploy helper puts selected changes on dev.** It checks the proposed changes, combines them with the latest shared work, and publishes the selected files to `dev`. The helper also coordinates the update to the shared test environment. Other edits can stay in the worktree for later. Checks and proof need to cover the version that actually ships to dev. [Dev publishing guide](../../.claude/skills/deploy/SKILL.md)
3. **Release preparation checks what would ship.** The release preparer checks workspaces and stalled deployments, compares `dev` with `main`, and reviews what customers can access. Marco confirms which changed features are ready, which stay off, and which need to be switched off. The release pull request is the formal request to bring the shared dev version into `main`, the production release branch. It comes after those decisions and the required checks. Marco merges it. [Release preparation guide](../../.claude/skills/create-pr/SKILL.md)
4. **Production rollout follows Marco’s merge.** That merge authorizes the rollout. The team uses the release built for that exact version, checks that the website and server will work together, and updates and verifies the server. The new website goes live after the required checks, including real guest and signed-in chats. The promotion process restores the previous website if the new one fails its live checks. [Production rollout guide](../../.claude/skills/update-prod-server/SKILL.md)

## 2. What “dev is not ready” means

The nightly helper sets the workspace verdict automatically. It returns “not ready” if it finds unfinished work that has neither been formally parked nor explicitly excluded with Marco’s agreement, a workspace it cannot account for, or a deployment still recorded as blocked. A temporary work area left by a failed deployment can also count while it is recent. Work already on dev or duplicated there passes this check.

**A formally parked workspace can stay unfinished through a release.** Parking saves a recovery copy and records why the work is waiting. The record must still match the workspace. Saving a recovery copy alone leaves it eligible to block. The nightly job can save a copy without making a decision to park it. [Workspace readiness rules](../../scripts/sessions.py) · [Recovery and parking rules](../../scripts/worktree_wip.py)

The release preparer still has to resolve conflicts, confirm feature availability with Marco, and verify the proposed release. A feature switched off can travel with a release if its inactive state is safe. A broken check that applies to the actual release or an unready feature customers could reach still needs attention. The feature review is deliberately broad. Today it flagged 62 possible feature areas, including 15 already disabled or unreleased, plus four changes it could not place. Those are review items, not a count of defects. [Feature review rules](../../.claude/skills/create-pr/SKILL.md#step-5--feature-readiness-gate-critical)

## 4. Why dev and main stopped fitting together

The last full dev release went into main on 23 November. Since then, five focused production fixes went into main through separate hotfix branches, covering voice and chat recovery, the service that handles replies, command-line publishing, chat cancellation, and voice-call reliability. At the comparison point, those fixes had not been brought back into dev through a merge of main. Dev had independently changed some of the same areas, including voice calls, cancellation and how the reply service starts. Some fixes addressed the same problems in different ways. The release process then had to decide which behavior to preserve, including where the two versions changed the same tests or release records. [Last full release](https://github.com/glowingkitty/OpenMates/pull/537) · [Reply service hotfix](https://github.com/glowingkitty/OpenMates/pull/539) · [Cancellation hotfix](https://github.com/glowingkitty/OpenMates/pull/543) · [Voice hotfix](https://github.com/glowingkitty/OpenMates/pull/544)

The earlier attempt reported ten conflicts and the team shipped a focused hotfix. A later trial comparison found thirteen conflicting files, concentrated in voice checks and plans, the reply service setup, and shared feature and release records. Those are two points in a moving release, rather than one fixed count.

## 5. A simpler flow with only dev and main

- **Keep dev safe to release.** Publish small, tested changes. Keep unfinished features off for customers and test that the switch actually prevents access and side effects, including through direct requests and from older apps. Test the existing experience with the switch off, too. Keep client-side encryption intact throughout. Work that cannot safely sit behind a switch stays in its private workspace.
- **Use dev for urgent fixes too.** A releasable dev makes the normal two-branch route usable for an urgent fix. Whenever main receives a production-only change, bringing main back into dev and checking the combined result is part of closing that incident. Do that before the next release or routine dev publication. With only two branches and a release request from dev to main, an isolated urgent release is impossible while dev contains a change that would be unsafe to ship. Restore the previous live version if needed, then fix or remove the unsafe change on dev and use the regular route.
- **Set a weekly release cut-off.** Pause ordinary dev publishing at the cut-off. From that point, accept only release fixes, and recheck the exact version after each one. The release owner verifies that main and dev fit together, confirms which features are on or off with Marco, and checks the journeys customers will use. Open one ready-for-review release request. Roll out after Marco merges, verify production, and resume regular dev publishing. Move unfinished activations to the next release.
- **Make the workspace list a backlog.** Judge release safety on the actual contents of dev and on deployments that affect it. Keep a separate reminder for saved work, with an owner, a reason and a decision on each Task. For the twelve in the evening inventory, finish the small, independently useful changes when proven, including Apple Daily Inspiration and the release-check fixes worth keeping. Shelve inline Tasks, design phase 1, and remaining browsing and collaboration work until their next milestone. Have one owner compare the overlapping collaboration copies and match remaining hotfix work against what shipped. Delete a workspace only after confirming that its useful changes already shipped, are preserved elsewhere with a verified recovery copy, or were explicitly approved for discard.

**Example: inline Task cards.** A chat builds and tests cards in its own workspace. The deploy helper puts the safe part on dev so testers can use it, with customer access switched off. At the weekly cut-off the team checks that ordinary chat still works and that customers cannot open or create those cards. Marco merges the release, the team updates production, and the cards remain off. Once the team proves the full create, edit and reopen experience, including client-side encryption, it publishes a separate activation change to dev for the next release. After rollout, it verifies that a customer can use the cards with the expected access.
